# 校园二手交易平台 需求规格说明书

## 1. 引言

### 1.1 编写目的
本文档定义「校园二手交易平台」的功能需求与性能需求，作为设计、开发、测试与验收的依据。预期读者为开发团队、指导教师与评审人员。

### 1.2 项目背景
高校内二手物品交易频繁（教材、数码、生活用品等），传统 QQ 群 / 贴吧交易存在**信息零散、难以检索、缺乏信任、无结构化定价参考**等问题。本项目构建一个面向校园的二手交易 Web 平台，并提供 **AI 智能推荐与议价咨询**能力，提升交易效率与体验。

### 1.3 项目范围
- 覆盖：用户登录、商品发布/浏览/搜索、热门抢购、订单流转、关注与 Feed 流、附近商品、每日签到、商品浏览量统计、AI 智能助手。
- 不覆盖：真实支付、物流、实名认证、多校区跨校交易。

### 1.4 术语定义
| 术语 | 说明 |
|---|---|
| 抢购 | 热门商品（`is_hot=1`）的高并发下单，采用 Redis + 消息队列削峰 |
| Feed 流 | 关注卖家的上新动态推送 |
| 附近商品 | 基于 GeoHash 的距离排序查询 |
| Agent | 调用大模型（DeepSeek）的智能推荐与议价助手 |

## 2. 总体描述

### 2.1 用户特征
- 用户为高校学生（以学号作为登录凭证）。
- 单个用户可同时扮演**买家**与**卖家**。

### 2.2 运行环境
- 服务端：JDK 17 + Spring Boot 3.2 + MySQL 8.0 + Redis 5+ + RabbitMQ 3.13。
- 客户端：现代浏览器（Chrome / Edge），前端 Vue3 + Element Plus。

### 2.3 设计约束
- 采用前后端分离架构，后端通过 RESTful API 提供 JSON 数据。
- 商品详情查询需承受高并发，须用 Redis 缓存并解决缓存三大问题。
- 抢购须保证**不超卖、不重复下单**。

## 3. 功能需求

### 3.1 用户模块（登录注册）
| 编号 | 功能 | 描述 |
|---|---|---|
| U-01 | 发送验证码 | 输入学号，后端生成 6 位验证码存入 Redis（2 分钟有效），开发模式返回明文 |
| U-02 | 登录/自动注册 | 校验验证码后，学号不存在则自动注册，签发 token 存入 Redis（30 分钟有效） |
| U-03 | 当前用户 | 根据 token 返回登录用户信息 |

### 3.2 商品模块
| 编号 | 功能 | 描述 |
|---|---|---|
| G-01 | 商品列表/搜索 | 分页、按分类筛选、按标题/描述关键词搜索、按价格排序 |
| G-02 | 商品详情 | 查询单件商品，命中缓存直接返回；缓存空值防穿透、互斥锁防击穿、TTL 随机防雪崩 |
| G-03 | 发布商品 | 登录后发布，含经纬度、成色、库存、是否热门；发布后写入 GEO 索引并推送给粉丝 Feed |
| G-04 | 更新/下架商品 | 仅卖家可操作，操作后删除缓存 |
| G-05 | 热门商品列表 | 查询 `is_hot=1` 的在售商品 |
| G-06 | 附近商品 | 按用户经纬度 + 半径，基于 GeoHash 返回距离内商品 |
| G-07 | 商品 UV | 商品独立访客量（HyperLogLog） |

### 3.3 抢购与订单模块
| 编号 | 功能 | 描述 |
|---|---|---|
| O-01 | 普通下单 | 登录后购买商品（不能购买自己的商品），生成订单 |
| O-02 | 抢购下单 | Lua 脚本原子判断库存 + 去重 + 扣减，成功后发 RabbitMQ 消息异步落库削峰 |
| O-03 | 我的订单 | 查询当前用户作为买家的订单 |
| O-04 | 订单状态流转 | 已拍(1) → 面交中(2) → 已完成(3) / 已取消(4) |

### 3.4 社交模块
| 编号 | 功能 | 描述 |
|---|---|---|
| S-01 | 关注/取关 | 维护关注集合与粉丝集合（Redis Set） |
| S-02 | 是否已关注 | 判断是否关注某用户 |
| S-03 | 共同关注 | 两个用户关注集合的交集 |
| S-04 | Feed 流 | 关注卖家上新时，将商品 id 推送到粉丝收件箱（ZSet 按时间倒序） |

### 3.5 签到与统计模块
| 编号 | 功能 | 描述 |
|---|---|---|
| SG-01 | 每日签到 | BitMap 记录当月签到，每天签到得积分 |
| SG-02 | 连续签到天数 | BitField 统计连续签到天数 |

### 3.6 AI Agent 模块
| 编号 | 功能 | 描述 |
|---|---|---|
| A-01 | 智能商品推荐 | 取在售商品候选，拼 prompt 调 DeepSeek，返回 3 个带理由的推荐 |
| A-02 | 智能议价咨询 | 取目标商品 + 同类商品价格，回答用户"价格是否合理"等问题，数据不足时明确说明不编造 |
| A-03 | 失败降级 | AI 不可用时返回友好提示，不影响其他功能 |

## 4. 非功能需求

| 类别 | 需求 |
|---|---|
| 性能 | 商品详情在缓存命中时响应 < 100ms；抢购库存扣减原子、不超卖 |
| 并发 | 抢购场景支持多用户同时下单，异步落库削峰 |
| 安全 | 密码/密钥不入库不明文提交；token 过期校验；越权操作（改他人商品/订单）被拒绝 |
| 可用性 | AI 模块降级可用；核心交易流程不依赖 AI |
| 可维护性 | 前后端分离，模块化分层（controller/service/mapper），统一响应结构 |
| 可扩展性 | Agent 模块独立，便于更换模型或接入更多智能能力 |

## 5. 关键用例描述

### 用例 1：用户抢购热门商品
- 参与者：登录用户
- 前置条件：存在 `is_hot=1` 且库存 > 0 的商品
- 主流程：
  1. 用户进入抢购页，点击「立即抢购」。
  2. 后端执行 Lua 脚本：判断库存 > 0、判断未重复下单，扣减 Redis 库存。
  3. 返回"抢购成功，订单生成中"，同时消息入队。
  4. 消费者异步创建订单、扣减数据库库存，库存为 0 时下架。
- 异常流：库存不足返回"手慢了"；重复下单返回"请勿重复下单"。

### 用例 2：AI 议价咨询
- 参与者：登录用户
- 主流程：
  1. 用户在商品详情页或 AI 助手页输入问题。
  2. 后端取目标商品信息 + 同类商品价格区间。
  3. 拼接带约束的 prompt 调 DeepSeek。
  4. 返回带数据依据的建议。
- 异常流：AI 不可用时返回"咨询助手暂不可用"。
